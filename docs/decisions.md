## D277 — crafting discovery is PICKUP-GATED by ingredient TYPE, not combine-to-discover (2026-07-08)

**When**: the user asked to replace the Session-TT combine-to-discover crafting (throw items into 4 input slots, hash the multiset, first successful craft unlocks the recipe) with a Deep-Dish-Dungeon-style model.
**Decision**: a recipe unlocks the moment the player has EVER collected all of its ingredient TYPES (counts gate craftability, not the unlock). Track it in a NEW monotonic `InventoryState.collectedItemTypes: Set<ItemId>` updated inside `inventory.addItem` (so pickup, craft-output, and loot ALL count — "collected = obtained by any means", which is load-bearing: `rope` is crafted not picked up, yet `sled_kit`/tents need it, so crafting a rope must unlock them). `recipeDiscovery.recipeCardState` returns cold/warm/unlocked; `unlockNewlyEligible` appends to `discoveredRecipes` on each acquire + fires one batched discovery chime/toast. SAVE_VERSION 15→16 (additive; pre-v16 saves seed `collectedItemTypes` from their already-discovered recipes' ingredients so nothing re-locks). The `craftingMenu` becomes a card grid; the multi-match chooser + partial-match hints + the TAB recipe book are DELETED (a collision like fire_kit/signal_flare is just two independent cards now).
**Why**: the combine-to-discover base interaction never explained itself — it accreted three compensating helpers over many sessions (partial-match hints AAV, the right-side recipe panel AAW/ABE, the TAB book AAA), the tell that it wasn't intuitive. Pickup-gating couples discovery to gathering (the survival loop's core), dissolves the chooser complexity, and makes a legible card grid. The tutorial machete beat gets cleaner: pick up the scattered scrap+cloth → the card unlocks → craft, vs "guess the combo".
**Considered alternatives**: count-based unlock (rejected — you'd need to have once held 4 scrap to SEE the locker recipe; annoying + weird). Keeping the input slots alongside the grid (rejected — two ways to craft, more to maintain; the user chose full replace). Grow-in grid with no "?" cards (rejected — the user chose the hybrid tease: cold `?` cards + warm "scrap + ?" reveals).
**friction-score:** 2 (save-schema touch is additive + migration-tested; the model is monotonic so no regression class; the only open knob is whether a 19-card `?` grid reads as a grind-checklist — a cheap follow-up dim if so).

## D278 — desktop distribution via Tauri v2 (not Electron); csp:null for the WASM/blob runtime (2026-07-08)

**When**: the user chose "ship it — desktop app" as a work cycle. The platform-decision-brief already recommended Tauri; this D-entry records the shipped choices.
**Decision**: wrap the identical Vite build as a Tauri v2 desktop app (`src-tauri/`). Key calls: (a) **Tauri over Electron** — single-player, procedural-only, no in-process Node server → the ~8 MB system-webview bundle wins over Electron's 100–240 MB (Electron only earns its weight for full-Steamworks Steam or host-and-play MP, neither on the roadmap). (b) **`app.security.csp: null`** — the game loads Rapier WASM (`wasm-unsafe-eval`) and Vite emits blob: workers + data: URIs; a restrictive CSP black-screens the app. Null for v1; tighten to a scoped policy later. (c) **`mainBinaryName: "Dustfall"`** so the output binary is `Dustfall.exe`, not the Cargo crate name `app.exe` (crate stays `app`; cosmetic, no main.rs churn). (d) **`build:desktop` = `cross-env VITE_BASE=/ vite build`** — the desktop build needs base `/` (Tauri app-root protocol), but `vite.config.ts` reads `process.env.VITE_BASE` DIRECTLY (no `loadEnv`), so a `.env.desktop` file would NOT reach `base` — it must be a real shell env var (hence cross-env). The GH-Pages `/Dustfall/` build stays byte-identical. (e) **localStorage saves kept for v1** (persist per-app in the WebView2 data dir); file-based saves via the Tauri `fs` API are a noted follow-up (an uninstall wipes localStorage).
**Why**: the brief's staged recommendation ("stay web + wrap for distribution regardless") — a desktop tier is cheap (~days once the toolchain exists), orthogonal to perf, and buys itch/Steam distribution + no tab-throttle + a real window. NOT a perf fix (WebView2 is the same Chromium/WebGL runtime).
**Considered alternatives**: Electron (rejected — bundle size, no Node need). Renaming the Cargo crate `app`→`dustfall` (rejected — `mainBinaryName` does it without touching main.rs/lib.rs). WebGPU/Godot (out of scope — brief gates them behind a measured frame ceiling not yet demonstrated).
**friction-score:** 2 (additive — `src-tauri/` + two devDeps + scripts, no `src/` change; the toolchain install needed admin/UAC which the agent shell couldn't grant non-interactively — the user approved one UAC prompt).

## D279 — cockpit "wrap" glass (side closures + roof) uses a FLAT unlit tint, not the sheen-y front-window material (2026-07-08)

**When**: playtest round ACN — after glassing the cockpit dome's side closures + crown roof, the user flagged view-dependent bright-"triangle" artifacts on the tilted overhead/side panes (looking up lit a single pane; a "streak" earlier).
**Decision**: split the cockpit dome glass into TWO materials. The **front window panes** keep `_glass` (MeshStandard + the onBeforeCompile curved-sheen/Fresnel presence term, tuned per the 2026-07-07 haze-parity work). The **wrap glass** — both side closures AND the crown roof cap — uses a NEW flat unlit `_glassRoof` (MeshBasic, dark tint, opacity 0.12, DoubleSide, depthWrite:false), pushed into its own buffer/mesh (`roofV` → `domeGlassRoof`).
**Why**: `_glass`'s sheen is view/grazing-angle dependent and was tuned for the FACE-ON front window. On the steeply-tilted side/overhead panes, looking up hits them at a grazing angle → the sheen spikes and lights individual panes as bright triangles (only visible at the real low opacity; a cranked-opacity diagnostic looked uniform, which is what proved it was the sheen term and not overlap/geometry). An unlit flat tint is identical from every angle → every wrap cell reads the same. Bonus: `_glassRoof` is DoubleSide, which subsumes the side-closures' earlier hand-wound double-face (needed so they render from the back-of-cockpit vantage without culling to a hole).
**Considered alternatives**: reducing the sheen intensity globally (rejected — would detune the front window the presence term was built for). Per-pane vertex attribute to gate the sheen (rejected — heavier than a second material for a peripheral surface). Leaving it (rejected — the user circled it twice).
**friction-score:** 2 (isolated to the dome-glass build; reversible; the one watch-item is that the wrap tint (flat 0.12) and the front sheen glass can read slightly different at their shared seam — acceptable, front is the hero surface).

## D280 — the cockpit glass envelope SEALS to the collar/shell forward ring by construction (2026-07-08)

**When**: playtest round ACN — the user found (a) a see-through wedge where the side glass met the hull, then (b) the dome was open above the crown ring, then (c) thin slivers at the top-outer dome↔ceiling corners.
**Decision**: make every edge of the dome glass envelope land ON the opaque hull's collar/shell forward ring (`hullProfile(COLLAR_Z)` = `cprof`), by construction, rather than near it. Side closures: collar-side edge = `collarPtAtY` with a small OUTBOARD overlap `CLOSURE_OUT=0.05` + `CLOSURE_AFT=0.03` (was landing 0.04 INBOARD → the gap; an earlier over-correction to 0.22 pushed PAST the shell and opened the top slivers, hence the dial-back). Crown roof cap: each pane's aft edge is sampled onto `cprof` by X (`roofAftPt(side, |crownNode.x|)`) so the glass meets the ceiling's forward edge exactly. Roof meridian ribs added at the intermediate crown nodes so every roof-pane edge sits on a mullion.
**Why**: "connect to the hull with no gap" is a geometric guarantee, not a visual tune — anchoring the glass edges to the SAME ring the opaque shell starts from means glass-front meets hull-aft along a shared line with a hair of overlap, so no daylight leaks at any vantage. Sampling the roof aft edge by X (not by a fixed fraction/collar point) makes it hug the shell's curved forward edge, which is what closed the top-outer slivers a straight fan left open.
**Considered alternatives**: an opaque hull filler wedge at each seam (rejected by the user — "keep it glass"). A single fan from the collar-crown point (rejected — chord gaps at the outer corners). Bigger `CLOSURE_OUT` overlap (rejected — over-pushing past the shell reopened the top slivers).
**friction-score:** 2 (visual/geometry, reversible; future dome-shape edits — `DOME_*`, the collar profile, or the shell forward ring — must keep these edges coincident or gaps return; the tunables are labelled in `shipScene.ts`).

## D281 — seed-spawned pickups render via InstancedMesh POOLS; the raycast resolves instanceId→pickupId (2026-07-09)

**When**: campaign "Sharpen & Deepen" cycle 1 (M1). Probe baseline: 371 world pickups as individual Meshes ≈ 43% of the 852 draw calls; the C59 backlog measurement had flagged the dense-view worst case.
**Decision**: STATIC seed-spawned branch + scrap render as instances in shared `InstancedMesh` pools (1 scrap + 5 branch-variants; module-level in `pickups.ts`; capacity 384 / 96×5 with a legacy-Mesh overflow fallback so no seed can lose pickups). `Pickup.inst = {pool, index}`; `mesh` points at the SHARED imesh (never scene.remove it; never tag it with a single `pickupId` — it would alias every instance). The interaction raycast pushes each pool ONCE into targets and resolves instanced hits via `intersection.instanceId → imesh.userData.instanceToPickupId[i]` BEFORE the parent-chain walk. `despawnPickup` frees slots swap-with-last (dense `[0,count)`) and fixes the moved pickup's `inst.index`. Rand-draw order per spawn kept byte-identical (variant, yaw, bobPhase) so seeded worldgen doesn't shift. Dropped/dynamic/canteen/relic pickups keep individual meshes (few, or physics-bodied).
**Why**: draw-call flattening — a dense wreck-field view no longer costs 1 draw per pickup (the probe camera only showed −35 calls because per-mesh frustum culling was already hiding ~330 off-screen pickups; instancing trades that cull, +70K always-drawn tris, for a flat worst case — tris are cheap here, calls were the bottleneck). Verified end-to-end by the NEW permanent `pickup-take-sweep` rig-shot gate (teleport → aim → real KeyE; the swap-with-last fixup case explicitly; an id↔slot bijection invariant).
**Considered alternatives**: per-instance frustum culling via chunked grid pools (rejected — over-engineering for ~70K tris). Keeping hidden per-pickup raycast proxy Meshes (rejected — double bookkeeping; the instanceId resolver is smaller). DynamicDrawUsage chosen over Static because takes rewrite matrices.
**friction-score:** 2 (the pools are module-level state living across a page session — a future in-session world REBUILD (not page-reload) would double-fill them; today every new-game/load path page-reloads or prunes via despawnPickup, and the overflow fallback + take-sweep gate would surface it. Harness lesson embedded in the gate: read `ctx.player.body` LIVE after enterGame; enterLive defaults 3P; re-pin aim per frame while the body settles.)

## D282 — shade relieves THIRST (not sun-drives-thirst); occluder threshold decoupled at 2.5m (2026-07-09)

**When**: campaign "Sharpen & Deepen" cycle 2 (M3 survival depth — the C31 follow-up + the Arc C1 water/exposure half).
**Decision**: (a) sun-occluder registration threshold = NEW `SUN_OCCLUDER_MIN_HEIGHT` (2.5m), decoupled from the C28 silhouette constant (8m); procgen POIs + wreck-yard hulks register post-placement bboxes (static boot sites only — NOT meteor-crash/debug spawns, whose teardown would leak stale occluders). Coverage 3→51. (b) Water/exposure is modelled as **shade RELIEVING thirst** (`THIRST_SHADE_RELIEF` 0.8, daytime + !inShelter, lerped by `sunExposure01`) rather than sun ACCELERATING it.
**Why**: (b) is the load-bearing call — a sun-accelerates-thirst factor would compound with `THIRST_HEAT_FACTOR` and shift the C38-approved heat band (~7.5→~6 min, dehydration stacking on heatstroke) — an autonomous change to a human-ratified curve. Relief-in-shade gives the SAME player decision (seek shade to conserve water) with all four probe bands unchanged by construction: the probe's thirst/hunger/prepared envs run `inShelter=true` (relief gated off), heat runs `sunExposure01=1` (relief ×1), cold runs at night (daytime gate). Verified: bands byte-identical + a new `heat-shade` probe env (survives midday in shade, minHealth ≥0.95) + coverage ≥20 asserted in the gate.
**Considered alternatives**: sun-drives-thirst (rejected — band drift, above). Registering meteor-crash wrecks as occluders (rejected — `resetMeteorCrash` teardown would orphan them; static boot sites only). Registering rock scatter (deferred — instanced pools lack per-instance bboxes handy; most rocks < 2.5m).
**friction-score:** 1 (pure tuning + registration; reversible one-line; the only watch-item is occluder count growth if future content spams `addHorizonSilhouette` — the slab test is ~51 AABBs per throttled tick today, fine).

## D286 — buried_pipeline beds at a FIXED depth (not a terrain-woven undulation); a rigid POI group has no heightfield access (2026-07-09)

**When**: campaign "Sharpen & Deepen" cycle 6 (M6 POI-breadth, sub-task A2 of `docs/feature-poi-archetypes.md`).
**Decision**: add a `buried_pipeline` archetype — a manifold hub (`pipeJunction`) + a run of pipe cylinders (`pipeSegment`) laid along a line. The "buried/surfacing" read is baked at a FIXED bedding depth in the ASSEMBLER (lower ~third of each pipe below the group plane, one segment humps proud, the far segment pitches down + sinks) — NOT a sine undulation that tries to weave under the sand. Hub + panel kept fully proud (the terrain-audit checks salvage panels). Wired into all biomes ~0.04-0.06, `derelict` shaved to keep tables ~1.0.
**Why**: the first pass used `yc = amp*sin(phase)` and floated the crests ~1.5m ABOVE the sand — because a procgen POI is a RIGID group placed at ONE anchor transform (the assembler gets no `terrain`), so it physically cannot dip segments under the REAL undulating heightfield 15m away (that spot could be +2m or −2m). The visual gate caught the float immediately. A fixed shallow bedding (breach ≤ half a radius) is robust at every anchor because the local terrain supports it — the same principle as wrecked_tank's `buryFrac` half-sink, applied per-segment.
**Considered alternatives**: per-segment `terrain.heightAt` sampling in the assembler (rejected — the assemble signature is terrain-free by design (D208 determinism: assembly is a pure function of seed); threading terrain in would let placement noise leak into the seeded stream). `burySink:true` with `buryFrac` (rejected — sinks the whole group incl. the hub's salvage panel below sand → terrain-audit fail). A taller sine amplitude (rejected — that IS the float bug).
**friction-score:** 1 (self-contained; the mix shift changes which POI a world-seed rolls, re-derived fresh by verify:placement; the bedding depth is the one feel knob if a future pass wants it more/less exposed).

## D288 — Infinite Sands S1: terrain streams as an 800m ANCHOR-MARGIN tile ring; content streams separately at 112m (2026-07-11)

**When**: campaign "Infinite Sands" cycle 1 (S1 ChunkManager spike, `docs/feature-infinite-procgen.md`).
**Decision**: two independent streaming grids. TERRAIN keeps its 800m/192-cell tiles, re-keyed to an unbounded integer grid with a 3×3 ring (`TERRAIN_TILE_RADIUS` 1) following an ANCHOR tile; CONTENT (S1 markers, S2+ POIs/scatter) streams on a NEW `chunkManager.ts` grid at `CHUNK_SIZE` 112m / `CHUNK_LOAD_RADIUS` 3 (the user-approved charter numbers). Both rings anchor-follow: the anchor only re-centers when the player moves MARGIN meters (terrain 24 / content 8) past the anchor cell's edge; everything outside the ring disposes immediately relative to the anchor (mesh geometry + every Rapier body — rule 9). S1 spike content = seed-tinted marker posts, OFF by default in normal play. One SHARED terrain material across all tiles (per-tile materials leak a `_shaderRefs` entry per build — never released).
**Why**: terrain at 112m would need ~361 tiles for the ~1200m visual horizon (draw calls) or an LOD scheme (S6 scope); at 800m the 3×3 ring is the SAME geometry the fixed grid shipped, so the released intro region boots byte-identical (placement gate 0-fails ×5 seeds proved it) and the horizon coverage matches today's. Content at 112m matches the fog-faded detail distance and keeps per-chunk teardown small.
**Considered alternatives**: a unified 112m grid for both (rejected — terrain draw-call/LOD blowup, and re-chunking the heightfield risks the intro region's byte-identity). A settle-frame-counter trim instead of anchor-margin (BUILT FIRST, rejected — the streaming probe caught that a player standing at a chunk CORNER micro-slides across the boundary every few frames, resetting the counter forever; the retained band never trimmed. The anchor-margin model is immune by construction and also deletes the dual load/unload radii).
**friction-score:** 3 (foundational for S2-S6; the known cost is the ~100-200ms per-tile bake blocking its frame at ring crossings — explicitly S6's rung, do NOT band-aid it earlier).

## D289 — heightAt answers ANYWHERE: baked bilinear inside loaded tiles, closed-form fallback outside (2026-07-11)

**When**: campaign "Infinite Sands" cycle 1 (S1).
**Decision**: extracted the full height formula (dune sample × biome flatness − sarlacc/cave carves) into ONE `computeHeightAt(x,z)`; tile baking samples it per-vertex and `heightAt` falls back to it for coordinates outside the loaded ring (previously returned 0 past ±1200m).
**Why**: S2-S4 procgen must query height at chunks that aren't loaded yet (placement ahead of the player); a 0-fallback would seat far content on a phantom plane. One formula = baked and computed heights always agree (the streaming probe asserts collider-vs-heightAt at +1500m).
**friction-score:** 2 (the fallback is pricier than the bilinear — fine for placement queries, but do NOT put it in a per-frame hot loop for many entities; if that need appears, pre-warm the tile instead).

## D290 — chunk determinism gates on the DESCRIPTOR, not the render: describeChunk is the single source (2026-07-11)

**When**: campaign "Infinite Sands" cycle 1 (S1).
**Decision**: a chunk's content is derived ONLY via `describeChunk(cx,cz)` — a pure function of `chunkSeed(worldSeed,cx,cz)` (murmur-style avalanche) with a FIXED rng draw budget (D226 discipline); `loadChunk` merely renders the descriptor. **Why**: gating the pure descriptor makes determinism testable WITHOUT booting chunks (8 coord spreads incl. ±90071 in milliseconds) and forces the S2 POI port to keep placement data derivable-before-load (which the save-diff model in S5 also needs).
**friction-score:** 2 (S2 must resist the temptation to compute placement inside loadChunk with scene state — anything not in the descriptor won't be covered by the determinism gate).

## D308 — streamed cave holes BAND-DECOMPOSE the heightfield instead of re-baking a trimesh (0.3 vs 24.4ms), which buys the hole-iff-resident invariant (campaign DEEPER cycle 8, 2026-07-27)

**When**: the density cycle. D307's entrance mechanism — swap the entrance chunk's heightfield collider for a full-tile TRIMESH carrying a carved hole — is affordable exactly once, at `createTerrain` time, for one hand-placed cave. Cycle 8 makes caves a regular rocky-terrain feature (`CAVE_SITE_CHANCE` 0.60, measured ~3.0-3.4 caves per travel-hour), so holes have to OPEN AND CLOSE during travel. This entry amends D307's mechanism for every cave except the origin one.
**Measured first** (this machine's `rapier3d-compat` build, 192×192 cells, `terrain.ts:490-506`): full-tile trimesh with 1 hole = 73,728 tris = **24.4ms** · plain heightfield, no hole = **0.2ms** · **band-decomposed sub-heightfields, 1 hole (×4 colliders) = 0.3ms**, 3 holes (×10) = **0.3ms**. **80× cheaper.**
**Decision**: a Rapier heightfield cannot carry a hole (parry's per-cell status bitvec is not exposed by the JS bindings — checked, not assumed), but a SUB-RECTANGLE of the height matrix is itself a perfectly good heightfield. So a holed tile becomes a handful of heightfields tiling everything the holes don't cover: row bands split at the holes' i-extents, and bands containing a hole split again along j. Adjacent pieces SHARE their boundary vertex row, so there is no seam and no gap — the collision surface is the same sheet, minus the holes (`terrain.ts:addBandHeightfields` / `attachTileColliders` / `rebuildTileHoles`).
**What the 80× actually buys is the INVARIANT, not the milliseconds** (`terrain.ts:187-206`): **a hole exists in the terrain sheet IF AND ONLY IF the cave beneath it is a live resident.** There is therefore never a state where a player can walk into an opening with nothing under it. That is strictly stronger than sealing an empty slot with a plug, and it costs nothing extra — the sheet is simply intact until the cave arrives. It is only reachable because open/close is 0.3ms: at 24.4ms per toggle the hole would have to be baked in for the tile's lifetime, and "an opening onto nothing" would be a state the game could actually be in. Both `addCaveHole`/`removeCaveHole` are ATOMIC with respect to the frame (rule 9): the tile's visual index buffer and its whole collider set are replaced inside one call, so the ground is never drawn open while it is still solid, or vice versa.
**The origin entrance tile deliberately keeps the OLD path** — full-tile trimesh + baked holed index buffer, untouched. Not because it is the better representation (it isn't) but because it is the collider the crevice weld and the descent were tuned against across cycles 4 and 7, and the released origin world has to come out byte-identical. `CAVE_SITE_ORIGIN_CLEAR_M` (1150m, `tuning.ts:1354` — the same radius as the streamed-POI exclusion) guarantees no streamed site can land on the origin tile, so **the two paths can never meet on one tile**. That mutual exclusion is what makes keeping both safe rather than a fork waiting to drift.
**Verification**: teardown proven EXACT — `restoreMax 0.0000m` (the restore re-derives from the same stored height array, so a closed hole is bit-identical to a tile that never had one), 0 rays through the sheet outside the hole, registries back to baseline, re-entry bit-identical; origin parity digests byte-stable; `holeStats()` exposes opens/closes/rebuilds/`maxRebuildMs` to the gates. One defect was found by CODE-READING inside the same cycle and closed by construction: the carved hole CLAMPS TO ONE TERRAIN TILE, so ~1.6% of sites would have shipped a visible-but-unenterable cave **with every gate green** — fixed by a tile-seam rejection that shares ONE `rawHoleCells` derivation with the hole block itself, rather than a second copy that could disagree.
**Considered alternatives**: (a) extend D307's trimesh swap to every streamed tile — rejected on the 24.4ms measurement (a hole toggle every ~90s of rocky walking is a visible hitch, and it would have forced the hole to be permanent); (b) leave a permanent hole and plug it with a lid collider when the cave is away — rejected: it is weaker than the invariant (a lid is a thing that can be wrong) for no saving; (c) patch parry's per-cell status bits — not available through the JS bindings.
**friction-score:** 2 (the decomposition is contained in `terrain.ts` and the invariant is the safety property the whole density cycle rests on; the residual is that two hole paths now coexist BY DESIGN and only the 1150m clearance keeps them apart — a future decision to stream caves near origin, or to move the origin cave, has to retire the trimesh path rather than let the two meet on one tile).

## D309 — the cave build is ONE job with TWO drivers (sync = infinite budget), and `finalize` is atomic; plus why boot-time shader warming provably cannot work (DEEPER cycle 5 + the cycle-8 addendum, 2026-07-25/27)

**When**: walk-test defect D-4 — *"will also need to preload the caves on the starting loading screen so it doesn't slow down the game as much when it loads in"* (Zach, 2026-07-24). What was missing was the LOADING SCREEN (`#boot-overlay`, inline-styled so it paints before the module bundle). The real scheduling problem is every OTHER cave, which builds during travel.
**Decision**: `buildCaveSdf` and `spawnCave` become thin wrappers that drive `startCaveSdf` / `startSpawnCave` with an **infinite budget** (`caveSdf.ts:193-201`, `caveGen.ts:2103-2114`); the streamed driver runs the SAME job at `CAVE_BUILD_SLICE_MS` (8ms). Nothing is re-implemented, so **the synchronous and the sliced output cannot diverge by construction** — and the gate proves it rather than trusting it (the origin junction+seed rebuilt through the SLICED path must produce the same `caveDigest` as the synchronously-preloaded original). Divisible stages (`sdf:field` per 8³ block · `sdf:cells` / `sdf:quads` per k-plane · `sdf:cut` per 3k tris · `sdf:color` per 7k verts) suspend without changing iteration order or arithmetic; `graph` / `sdf:geom` / `dress` / `finalize` are atomic (`caveStream.ts:167 ATOMIC_STAGES`). Slicing changes only WHEN work runs, never WHAT it computes — and that was MEASURED, not asserted: a git worktree at the pre-refactor commit reports seed 1337 `digest=a5d75db9 nodes=11 tris=94927`; after the refactor, and through the sliced path, both report `a5d75db9` / 94,927.
**The atomic finalize.** `doFinalize` (`caveGen.ts:2373`) bakes the Rapier trimesh and calls `scene.add(group)` in the SAME step, so a cave is never visible without being solid and never solid without being visible — not for one frame (rule 9, the terrain-tile precedent). This is also why the two budgets are reported and gated SEPARATELY: a ~97ms atomic bake must never be able to hide inside an 8ms slice budget.
**The honest ceiling, stated instead of laundered.** Measured before→after on a streamed build (seed 1337, GPU headless): worst frame **~1160ms (≈70 frames of hitch) → 90.5ms observed**; worst divisible slice 17.7ms; worst INDIVISIBLE step **97.6ms — `finalize`**; steps per build 1 → ~84. **~90-100ms is the floor and no slicer can lower it**: a single `ColliderDesc.trimesh` call over ~70k triangles is one call into WASM and cannot be chopped. That is a 13× cut, **not a fix**. Levers named and deliberately not taken: a coarser voxel for far caves, a convex-decomposed or per-chamber-heightfield collider, an off-thread collider build.
**Addendum (cycle 8) — the shader warm, and why the obvious fix provably cannot work.** `cave-density` seed 7 reported a reproducible worst frame of **1544-1667ms** against 87ms at seed 1337, and none of the build's own numbers came near it (tor 154-166ms, slices ≤16ms, the Rapier bake 81-84ms). Cause: `finalize` calls `scene.add` and the SAME frame renders a material whose program has never been compiled — `renderer.info.programs` went 101→103 across that one frame, both keys `cavePoolWater-v1` (transparent + DoubleSide ⇒ three needs the flipSided and non-flipSided builds). Warming at boot was TRIED AND MEASURED before this shipped: two materials byte-identical to a pool material, pinned FrontSide/BackSide, DID compile both variants — and the streamed cave still compiled two more, because **a three.js program key carries the SCENE'S LIVE LIGHT STATE** (boot keys read `numPointLights 33, shadowMapType 2`; the cave-build keys read `34` and `1`). No warm-up at a FIXED MOMENT can match a key that moves with the world. So the build scheduler warms **off-scene at the live state** (`compileAsync` before `scene.add`, `caveStream.ts:392-455`), with a frame-count fail-safe so a failed precompile costs exactly what a successful one costs. Gate-asserted: **0 programs compiled on the visible frame**. And "it's fine at seed 1337" was never safety — every cave has at least one pool, and the per-cave pool material is DISPOSED on eviction, so the stall returns for the next cave in the same session.
**Considered alternatives**: (a) a separate sliced implementation alongside the synchronous one — rejected outright, that is two code paths that will silently disagree and a digest gate that only catches it after someone notices; (b) make `finalize` non-atomic to smooth the spike (add the mesh first, bake next frame) — rejected, it manufactures exactly the "visible but not solid" frame rule 9 exists to forbid; (c) accept the 1.6s frame as a seed-7 quirk — falsified (see above).
**friction-score:** 2 (the wrapper shape is the cheapest possible divergence guarantee and is now the pattern any future cave-side job is expected to copy — the tor entrance build is the named next candidate, and it is currently NOT in any digest, so slicing it needs a digest FIRST; the standing residual is that the atomic bake is a hard floor, so cave density and travel speed stay coupled to it).

## D310 — INV-COLD: caves get colder by clamping the TARGET, in both directions — and the gate falsified its own plan's constant (DEEPER cycle 11, 2026-07-28)

**When**: Zach's ask — *"the temperature should be colder but not cold enough to damage the player."* The recon found this was not an addition but a **FIX**: underground the survival branch chain still ran off the SURFACE clock, so by day the shade-heat floor WARMED you and at night `COLD_NIGHT_DRAIN` walked you to −1 and killed you through fifty metres of rock. Exactly backwards.
**Decision**: a cave branch in `updateStats` (`survival.ts:91-112`) that **PRE-EMPTS** the sun / night / twilight branches and walks temperature toward `caveColdTarget(depth, kind, wet)` (`survival.ts:41-50`). Shelter still wins (the branch above it): light a fire or pitch a tent down there and the cold is fully neutralised — that is the verb the cold is asking for, and D312 is what makes placing a fire underground possible at all. Three properties carry the "never damages" guarantee, and each is deliberate:
1. **The clamp binds the TARGET, not the rate, and is applied LAST** — after the depth smoothstep and after every kind and wetness multiplier. No stacking of depth × kind × wetness × weather × time-of-day can escape `[CAVE_COLD_FLOOR, 0]`. The guarantee is true by construction, not by tuning; a rate clamp would only have made damage slow.
2. **The approach is monotone in BOTH directions** — a player who descends already frozen from a night trek is pulled UP toward the target. Warming is not a courtesy: it is the clause that makes "a cave can never damage you" TOTAL rather than conditional (and it is physically right — a cave sits near the local mean annual temperature).
3. **`depth <= 0` is exactly a no-op** (`if (!(depthM > 0)) return 0`), so the surface survival model is byte-identical to what shipped.
Plus a boot assert (`CAVE_COLD_FLOOR_OK`, `survival.ts:20-31`) holding `CAVE_COLD_FLOOR >= -1 + CAVE_COLD_SAFETY_MARGIN (0.35)` and `<= 0` — move the floor past the margin and the game screams at load rather than shipping a lethal cave.
**THE MEASURED DEVIATION — the gate falsified the plan it was built from.** `CAVE_COLD_FLOOR` ships at **−0.48, not the planned −0.55** (`tuning.ts:1274-1283`). The worst stack is flooded (×1.25) while standing in water (×1.25) at full depth = −0.45 × 1.5625 = **−0.703**, which any clamp catches — but a clamp at −0.55 lands OUTSIDE `HEALTH_REGEN_TEMP_MAX` (0.5), so the deepest wet cave **silently stopped health regeneration**, which the plan's own Q6 forbids. −0.48 satisfies Q5 (a −0.45 target at depth), Q6 (regen keeps running everywhere underground) and the safety margin at once, with MORE headroom to the damage line, not less.
**The plan's red-proof spec was ALSO wrong, and that is worth keeping.** It specified proving the damage assertion by driving the cold to −1.4. That cannot reach the damage line at all, because `CAVE_COLD_TARGET_MAX` is −0.45 and the clamp binds the target. The assertion was instead proven by temporarily setting `TARGET_MAX = −1.2` → **4,500 damage ticks, player died**; both values restored. A red-proof recipe written before the invariant existed can be as wrong as the constant it was meant to check — demonstrate the gate RED by whatever route actually reaches the failure, not by the route the plan assumed.
**Verification**: **CAVE-COLD**, riding the existing `pool-fill` leg (no 25th leg added), `pass=1` on both seeds: 112 real-tick cold cells with **`damageCells: 0`**, plus a direct sweep of `caveColdTarget` through a debug hook exposed for exactly that purpose (`debugPanel.ts:1216-1221`).
**Considered alternatives**: (a) an extra cold DRAIN on top of the ambient term — rejected, it stacks with night and cannot be bounded without bounding the rate, which only delays death; (b) clamp the player's temperature after the fact — rejected, that fights every other system for the same variable and hides the intent; (c) leave the surface model running underground and tune `COLD_NIGHT_DRAIN` down — rejected, it is the surface's number and would make desert nights harmless to fix a cave bug.
**friction-score:** 1 (one branch, one clamped pure function, a boot assert and a machine gate. The numbers — `CAVE_COLD_TARGET_MAX`, `_KIND_MUL`, `_WET_MUL`, `_RATE_PER_SEC`, `_DEPTH_FULL_M` — are Zach's taste dials and NONE of them can break the invariant, because the invariant is not one of them).

## D311 — a KCC march verdict is dt-coupled, so it runs SOLO in the gate's quiet phase; verdict integrity outranks the wall-clock target (DEEPER cycle 9, 2026-07-27/28)

**When**: building the tiered parallel gate runner (`scripts/verify-chunks.mjs`) — `verify:chunks` was ~90 min serial and the EFFICIENCY WATCH had set a ~35 min target.
**Decision**: **a KCC march is dt-coupled** — fewer frames per second ⇒ a larger per-step translation ⇒ different collision resolution — so machine load can flip a march verdict on marginal geometry. Therefore the criterion for running a leg alone in the quiet phase is "**the verdict can move with load**", **NOT** "the leg has a millisecond tripwire". Every march leg (`cave-walk` ×4, `cave-streamed` ×2, `cave-kinds`) is `solo: true` (`verify-chunks.mjs:238-244`, `:355-357`, `:380-395`); the parallel phase keeps only legs whose assertions cannot move with concurrency.
**The evidence — measured twice, never assumed.** (1) `cave-kinds` carries no millisecond tripwire, so the first parallel build ran it concurrently. It reported 23 fails where the serial runner reports 13: the known 13 PLUS 10 from `shaft`, whose march went `reached=0/8 ascent=FAIL` under load and `8/8` alone — **same site, same seed, same digest, byte-identical geometry stats** (slope 23.3° / head 2.72 / chamHead 3.26 / cover 12.48 in both). (2) Seed 7's interior: the **`a` half red at `jobs=4`** (reached 7/10, node 7→8 fwdClear 0.3-0.8) while the **`b` half passed GREEN in the SAME batch on the SAME stable digest**, and the same tree marched 10/10 serially. The escape hatch is measurement, not a threshold: `jobs=2` for marches, or splitting the quiet phase across machines).

## D312 — ONE placement-ground sampler for every placeable: cast against live colliders, snap to the analytic height (DEEPER cycle 11, 2026-07-28)

**When**: the recon for "deployable lanterns underground" — which found a **live, shipped, player-facing bug** instead of a feature to build, and found it by reading.

The ghost preview ring lied about it in exactly the same way, because it did the same arithmetic. Proof: the lantern now lands at **y −22.71 with collider identity = the cave body**; the old path gave **y +7.89** — thirty metres up inside rock.

**NINE sites, not the six the plan named.** A grep showed `largeTent` / `locker` / `stake` carry the identical line, and **fixing six of nine identical bugs is arbitrary** — the other three would have come back as a bug report a week later with none of this context attached. **Three details that are load-bearing** (all stated in the module header; each was learned the hard way elsewhere in this repo): (1) **the ray starts at the eye, not at y=100** — from up there it hits the terrain sheet first and never reaches the cave floor, i.e. the obvious implementation fails the exact case the module exists for; starting just above the camera means the first thing the ray meets is the first thing BELOW YOU, which is the definition of "the ground here" for someone standing under fifty metres of rock. ## D313 — the SDF grid origin snaps to a fixed world lattice — and the honest negative result: it was NOT the cause of the entrance failures it shipped to fix (DEEPER cycle 9, 2026-07-27)

After the snap the sample lattice is a pure function of WORLD POSITION and `voxel` and nothing else, so any given world-space geometry polygonizes identically no matter what else shares its field. Seed- and layout-independent by construction (D290): anchored at the world origin, never at anything the generator rolled.
**THE NEGATIVE RESULT — the durable half of this entry.** The snap was shipped **believing it was the cause** of the entrance marches. **It is not, and that was MEASURED, not assumed**: with the lattice stable the same three sites still fail at the same legs, the capsule stalls at the same coordinates to within 0.1m (flooded/1337 @(675,1113) stalls at (683.0,1111.6,y13.7) both before and after), and — the decisive A/B — the **CANONICAL kind fails identically at those same sites**. The entrance failures are SITE-dependent and kind-independent; the blocking surface is the tor, which this grid never touched. Two sibling hypotheses died in the same investigation and are worth recording as such: the **grid-origin theory** (falsified by A/B measurement before any churn shipped) and a **guard-sweep fix** (built, then proven a no-op). The real defect was found afterwards by a PURE clear-height model that swept ~410 real sites in seconds — **~1 cave in 9** pinched at the carved hole's far edge, exactly where the roof clamp hands over to terrain — and was closed BY CONSTRUCTION (hole 3→4 cells + a placement rule), not by the snap. The snap is what made a site-shaped failure look kind-shaped for a day.
**What it cost, deliberately**: every cave mesh including the origin cave shifts by up to one voxel and `caveDigest` re-baselines — **108af91c → d8f15005** and **ff8309a8 → 99e0015b** (the third deliberate cave-digest re-baseline of the campaign). The SURFACE world is untouched: terrain / chunk / placement digests do not move; only cave meshes requantize. Kept anyway on its own merits, because it removes a genuine latent coupling — a cave's entrance mesh silently depending on its own room layout — which would otherwise have kept manufacturing this class of confusion.
**friction-score:** 1 (contained in one function and strictly easier to reason about afterwards. Two residuals: any cave digest quoted in a pre-cycle-9 doc or comment is now stale — `caveKinds.ts:19` still names the OLD pair `108af91c / ff8309a8` as the origin-parity gate; and the standing reminder that a fix believed to close a defect must be A/B'd AGAINST the defect before it is credited with closing it).

## D314 — cave kinds are a PARAMETER TABLE over one generator, with the safety floors machine-asserted (DEEPER cycle 9, 2026-07-27)

**When**: the charter's kinds row — *"distinct parameter sets over the same generator so caves read as different places … not new code paths — a kind table."*
**Decision**: `src/world/caveKinds.ts` is ONE table of numbers plus a seed-pure assignment hash. `caveGen.ts` still runs exactly one algorithm (descending trunk → forced hall → egg chamber at the end → side pockets → cover/slope passes → SDF → dressing); every kind is that algorithm fed different constants. The two genuinely NEW capabilities (rubble heaps, scrap scatter) are built as GENERAL capabilities with a per-kind density whose **canonical value is ZERO**, so the code path is shared and the canonical cave stays bit-identical to cycle 8's.
**`canonical` is not a kind — it IS `tuning.ts`.** Every canonical field reads straight off `Tuning` with an EMPTY override object. That is load-bearing rather than decorative: the origin/egg cave builds with it and the origin-parity digests are a hard campaign gate, so **if a canonical field ever stops being a literal Tuning read, the origin cave moves and the gate goes red** — which is exactly the alarm we want. `canonical` also stays in the weighted mix, so the cave a player already knows keeps appearing beside the four new reads.
**What a kind may NOT spend, and it is machine-checked** — `assertCaveKindTable()` runs in dev at module load and throws with the reason attached (`caveKinds.ts:495-535`). Each rule is scar tissue this project already paid for once:
- **Corridor half-widths.** `CAVE_GEN_SQUEEZE_HALF_W` went 1.55 → 1.85 and `CAVE_GEN_GALLERY_HALF_W` 2.3 → 2.8 in UNDERWORLD cycle 3 because the KCC **wedged** against a corridor wall on a climbing backtrack at the old values. "A tight warren" is bought with corridor LENGTH, HEIGHT, chamber size and squeeze frequency — never by re-spending the wedge margin.
- **The corridor grade.** `CAVE_GEN_MAX_SLOPE` 26° sits under the march gate's 32° ceiling with the displacement margin already eaten. The "collapsed shaft" is vertical because it is DEEP with TALL rooms over a LONG trunk, not because its ramps are steeper. Every kind holds 26.
- **Headroom.** Corridor clear height ≥ 2.5m and chamber height ≥ tallest corridor + 1.0m (a corridor mouth has to fit inside the chamber's dome), against a 2.0m gate floor — plus the room hierarchy the march asserts on every kind (the egg chamber is the largest room).
- **Pool DEPTH is not a kind parameter at all.** Pool count and radius are (flooded runs 2-3 pools at ~1.7× the canonical radius); `CAVE_POOL_DEPTH_M` stays **0.26m for every kind** — you wade, you never swim, and the collider stays the visible floor rather than the water surface.
The alternative to `assertCaveKindTable` was a paragraph asking the next author to be careful; this project's own lesson is that **prose rules recur and machine gates do not**. A kind that violated one of these would BUILD, render, and pass every cheap check — then wedge a player in a corridor 4km from spawn where nobody is looking.
**Determinism (D290)**: the kind is a pure function of the site descriptor's own per-cell RNG stream, drawn inside `caveSiteInCell`'s FIXED DRAW BUDGET and AFTER the site's generation seed — so adding kinds moved no site by a millimetre and the cycle-8 placement digests are unchanged.
**Verification**: the `cave-kinds` gate forces all four kinds onto real descriptor-accepted sites through the shipped `requestSite` path and gives each the same march + void sweep plus kind-defining and CROSS-KIND DISTINCTNESS assertions — because a table that collapsed to canonical would march perfectly, so "green" had to be made to mean more. It carries a harness-side vacuous-pass guard too: a green row off zero built / zero marched kinds would launder "the kind table never produced a cave" as "every kind is fine".
**friction-score:** 1 (additive table over an unchanged generator, with its own machine check. Forward exposure: a fifth kind is a cheap table row, but a kind wanting a genuinely NEW capability must add it as a general capability with a zero canonical default — otherwise the canonical cave moves and the origin-parity gate reds, which is the intended outcome, not a surprise).

## D315 — a gate reads the GAME'S predicate, never its own copy of it (DEEPER cycle 12, 2026-07-29)

**friction-score: 1**

Whether a cave carries the dead-explorer beat is a field on the kind table (`deadExplorer`), read
through exactly one function (`caveKindCarriesBeat`). The BEAT-SITES gate asks the running game for
that table (`__game.caveKindTable()`) rather than testing `kind === 'warren'` itself.

**Why.** A gate holding its own copy of a predicate is not testing the game, it is testing its
agreement with a duplicate — and it stays green through precisely the change it exists to catch
(someone moving the beat to another kind, or onto `canonical`). The campaign has already paid for
this class twice (`open-end` vs the leviathan's front door; the vacuous collision check).

**The load-bearing consequence.** `assertCaveKindTable` holds `canonical.deadExplorer` false, so
"the origin cave never carries an authored corpse, therefore the origin-parity digests
(`d8f15005` / `99e0015b`) cannot move" is a **machine fact with two independent holders** — the table
assert (which halts boot by name; proven) and the BEAT-SITES origin tooth (proven). The beat is also
sink-spawned, so its meshes are outside `caveDigest`'s hashed set regardless. Belt, braces, and a
gate that reads the belt.

## D316 — an instrument that cannot move when the defect is fixed is not a gate (DEEPER cycle 12, 2026-07-29)

**friction-score: 2**

The dead-explorer tableau floated (journal 8.8cm, lantern 10.0cm, crate 5.5cm above the rock). The
bedding probe written to catch it measured `anchor-plane y − rock under each prop's nominal offset`.
That is a real quantity — the floor's gradient under the tableau — but it is **not a function of
where any prop is**, so after every prop was re-seated the probe reported *the same seven numbers to
the millimetre*.

**The rule.** Before trusting a measurement, ask what would have to change for it to move. If the fix
cannot move it, it is measuring something else. Both wrong versions here were plausible: the anchor
plane (which is what the *bug* was about) and, at the second attempt, the prop's **origin** — but a
tipped lantern rests on its cage and a flask on its rim, so both sit deliberately above their
origins, and origin-vs-rock reads a design offset as a defect. The question is "is there daylight
under this object", and the answer is its **bounding box floor** against the rock under its own
footprint.

**Corollary, from the same cycle.** The plan's mandated red-proof for the anchor tooth (seat on the
analytic plane — the historical bug) came back at **4.2cm, inside the 5cm bar**: the tooth would pass
a build with the old bug in it. That negative was recorded rather than papered over, and the response
was a *second* tooth that is red-provable, not a tightened threshold on the first (3.9cm is the
correct path's own reading — tightening would red the truth).

## D317 — one-time authored caches persist by DESCRIPTOR KEY, and by remaining CONTENTS (DEEPER cycle 12, 2026-07-29)

**friction-score: 2**

Streamed-cave pickups are `transient` by D299 — taken-state does not survive eviction. Acceptable for
six ambient scrap flakes; an infinite farm for an authored cache holding a `battery`. So cave story
beats persist in an additive optional save array keyed on the cave's **descriptor** key
(`cave:<gx>,<gz>`), never a runtime id (D292: a streamed cave's runtime identity dies with its
eviction, and a saved id could patch a different object after reload). **`SAVE_VERSION` stays 18 — no
migration.** The container is excluded from the id-keyed `lootContainers` array for the same reason
the streamed `salvageables` already are.

**Contents, not a `looted` boolean** (a deliberate strengthening of the cycle-12 plan's Q6): a boolean
only closes the exploit for a player who empties the crate in one visit. Take just the battery, walk
out, and a boolean keyed on "emptied" refills the whole cache. Recorded at **both** boundaries — save
*and* eviction — because the ordinary way to loot it is to empty it and save while still standing in
the cave, which the eviction path never sees; and a load taken while the cave is still resident
re-syncs the live crate, since loading does not re-run the sink.

## D318 — the rig serves the LIVE working tree: never edit source with a probe in flight (DEEPER cycle 12, 2026-07-29)

**friction-score: 3**

A probe run is not a snapshot. `npm run rig` starts Vite against the working tree, so a file saved
mid-run changes what is being measured. This was learned by doing it: cycle-12 source was written
during a flake-sampling window on the theory that editing is zero-CPU and therefore cannot perturb a
dt-coupled march. It is not about CPU. The run booted a half-written `main.ts` — it used
`buildDeadExplorer` two edits before the import existed — and died on a page error that looked like a
result.

**Rule: run → wait → edit → run.** It applies to `src/` (Vite serves it) and to concurrent agents:
an agent running probes and an orchestrator editing source are the same hazard wearing two hats.
`scripts/*.mjs` is read once at process start and is safe mid-run, but is unsafe to edit concurrently
with an agent that also owns it, for ordinary conflict reasons.

**The second-order lesson is the expensive one.** This mechanism was checked against the campaign's
open warren "regression" and did **not** explain it (the commits inside that gate window were
docs-only). But the timestamps falsified the premise the regression call rested on — the pause note
claimed the failing run was *"SOLO on a quiet machine (so dt-coupling does not explain it)"*, and an
agent was concurrently reading files and writing two commits. **"The machine was quiet" is a claim
that needs evidence, not an assumption**, and D311's dt-coupling was excluded on the strength of it.

## D319 — when N confident fixes each change nothing, the defect is a SUM: instrument the sum (DEEPER walk-test W-4.3, 2026-07-30)

**friction-score: 2**

The entrance's perimeter band survived SIX single-cause fixes — each mechanism real, each fix
correct, each visually null: the grid clip, the fin clip, cast shadow (A/B'd, exonerated), the
terrain datum (measured, exonerated), the smax pedestal, the relief floor, the hug ordering. Five of
those defects were genuinely present AT ONCE, each contributing 0.1-0.4m of rim height — so removing
any one left a band indistinguishable from before, and every fix "failed."

**The rule.** A visual defect that survives a correct fix is not evidence the fix was wrong — it is
evidence the defect has MORE THAN ONE parent. Stop fixing terms; measure the assembled quantity
(here: a live-tab transect of final rock-top minus terrain along bearings, then term-stack
arithmetic against the measured heights). And when the terms are many and future-open, the durable
fix constrains the SUM, not the parts — the feather now converges the TOTAL column to the hug band,
so any term added later is automatically inside the contract.

**Corollary for procedural height fields specifically:** smooth-max is not free — `smax(a,b,k)`
bulges by up to k/4 exactly where its arguments are close, which for ground-hugging terms means
exactly at the silhouette rim. Budget for blend pedestals wherever smax feeds a zero-crossing.

## D321 — the tor build is sliced with a GENERATOR, and its tooth asserts sync==sliced rather than a literal (cycle 13, 2026-07-31)

**friction-score: 2**

Three calls, each of which had a plausible alternative:

**1. A generator, not hand-hoisted closure state.** The cycle-13 plan budgeted ~200 touched lines in
`caveEntrance.ts` to hoist locals into closure state with a resumable `k` index — the pattern
`caveSdf.ts` uses. A generator gets the same result in ~25 touched lines, because the invariant we
need ("slicing changes only WHEN work runs, never WHAT it computes") is exactly what a generator
guarantees BY CONSTRUCTION: every local, loop counter and half-filled array is preserved by the
language at the suspend point. Manual hoisting is ~200 opportunities to typo a variable into the
wrong scope inside geometry that had just taken eight rounds of visual tuning. **Considered
alternatives:** the manual hoist (rejected: strictly more risk for the same outcome); leaving the tor
unsliced (rejected: it was the worst frame in the game).

**2. The tooth asserts sync == sliced, NOT a committed digest literal.** A tor digest legitimately
moves whenever entrance geometry is tuned — it moved eight times during the W-4 rounds alone — so a
literal would be re-baselined routinely, and a gate that gets re-baselined routinely teaches the
team to re-baseline it when it is right. What can NEVER legitimately differ is the same seed built
two ways. That invariant needs no maintenance, ever.

**3. `msTor` reports ACTIVE build time (the phase sum), not wall-clock since t0.** A sliced build is
parked across frames it did not consume; charging those to the tor would make the slicing read as a
10x regression in the very number that motivated it. The worst-FRAME number (`maxTorMs`) is
unchanged in meaning and is what the tripwire still watches.

**When:** cycle 13, the closing perf item.
**Why it matters beyond the tor:** the first run of the new gate went RED, and it was the
INSTRUMENT — the sync reference used the world seed and `holeRect=false` while `doTor` uses the
site's own seed and the rect lid, so it built a legitimately different tor and reported a geometry
bug. The gate was believed for about a minute. Any A/B tooth that REBUILDS a reference must mirror
its subject's construction arguments exactly, and the mirroring requirement now sits at the call
site as a comment.

**The honest limit, on record:** slicing does not put the tor under a 16ms frame budget and cannot —
~55ms of it is one `ColliderDesc.trimesh` bake, which no slicer chops. 255ms -> 58ms is the win;
"under budget" was never available and the plan was right to refuse to promise it.
